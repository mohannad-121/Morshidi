## Migration dependencies and recovery

**Production applied versus pending: UNVERIFIED for both projects.** An authorized database operator must compare the production migration ledger and schema/function definitions with the exact reviewed files, using read-only inspection first. Confirm target project identities independently. Do not infer production state from local test databases.

Morshidi's ordered chain consists of `0001_academic_catalog.sql` and the timestamped migrations through `20261021162616`. Notification dependencies include the universities/auth schema from the earlier chain, `20261004090000_university_live_sync.sql`, `20261005160000_create_student_university_identities.sql`, all applicable intervening ordered migrations, then `20261021162616_university_scoped_notifications.sql`. The complete 29-file chain was replayed in isolated Supabase during Phase 4D. The scoped migration revokes the old unscoped ingest RPC and replaces global uniqueness/version scope; old application code can no longer ingest after this migration and can still read old unscoped data if left serving. Therefore **quiesce notification reads and ingress across all old API instances before changing the schema**, and resume only after the scoped API is deployed and verified. The new API expects the scoped RPC and columns, so deploying it before the migration causes controlled failures. Receiver 503 responses should be retried by the new sender, but do not rely on an unobserved rollout race.

Fake University ordered migrations are `20261007111025_initial_university_schema.sql`, `20261007120629_university_transactional_rpc.sql`, `20261017155240_multi_plan_curriculum_foundation.sql`, `20261019143000_registration_audit_and_demo_offerings.sql`, the separately owned/pre-existing `20261021110000_fake_university_free_elective_patch.sql`, then `20261021161034_notification_reliability_idempotency.sql`. Investigate the independent free-elective patch and the real migration ledger before approving any pending files; do not skip or execute it merely to make this plan fit. The new sender requires the v2 registration RPC and delivery-state columns, so apply its reviewed migration before enabling the new worker. Pause old sender workers and inspect pending/terminal rows during the transition.

Before any approved migration, take and verify recoverable backups for both databases and document a restore/recovery owner, retention, service quiescence, and reconciliation plan. These migrations are forward-only: a code-only rollback is not automatically safe after the scoped receiver revokes the old RPC. Restoring a whole database can lose intervening legitimate writes; any restore or compensating migration needs a separately reviewed, data-aware plan. Preserve and inspect all pre-existing events. Morshidi's historical rows have unknown origin and remain `university_id IS NULL`, excluded from scoped reads; do not backfill by guessing. Historical no-op registration keys from before the university ledger cannot be reconstructed.

## Security, worker, and browser readiness

Local Phase 4D tested real Supabase Auth, PostgREST and FastAPI route behavior with synthetic A/B users, the same external student number in both universities, separate simulated trusted sender configurations, invalid HMAC, duplicate signed envelopes, and mapping deletion. A separate real Supabase upgrade test verified legacy quarantine, scoped uniqueness/version tracking, forced RLS and selected RPC grants. These were isolated local results; actual Fake University delivery and the browser/network path were not exercised. The receiver accepts only one configured university/HMAC pair per process. SSE rechecks Auth and the stored mapping each three-second polling cycle and closes when invalid; revocation is not instantaneous and a previously authorized in-flight batch can still arrive.

Fake University's Fastify worker starts a one-second unref'd timer with the API process, clears it on shutdown, reads at most 25 due events per batch, signs exact UTF-8 JSON with HMAC-SHA256, and marks 2xx as delivered. Unsupported and malformed events have durable terminal reasons and remain auditable; nontransient 4xx is terminal, while transport errors, 408, 425, 429 and 5xx retry with persistent exponential scheduling capped at 60 seconds. A per-row failure does not intentionally stop later rows. A historically unsupported event is terminalized and excluded from later batches; queue-fairness tests passed. A large queue or database failures can still delay events. Multiple worker instances have no distributed claim and can issue duplicate requests or race on delivery state; scoped receiver idempotency protects duplicate ingestion but operational behavior must be verified. A long-running Render process and durable Supabase backend are required; an idle/stopped process cannot deliver. Database scheduling persisted across separate PostgreSQL client processes in Phase 4B; actual PostgreSQL-backed worker restart and hosted restart were **not** tested.

The frontend reads SSE using authenticated `fetch`, and polls notifications every 60 seconds as fallback. It does **not** automatically reconnect a terminated SSE fetch; the server's `retry` line does not cause the fetch reader to reconnect. There is no Last-Event-ID resume; initial history is limited to 50 and the UI retains 30. Database sequence IDs need not equal transaction commit order. The SSE stream sends its initial retry frame but no periodic idle heartbeat. Before any broadcast, verify deployed CORS, bearer authentication, proxy buffering and idle timeouts, stream delivery in two browsers, behavior after an intentionally interrupted stream, 60-second polling recovery, page refresh and the stated history limitations. These remain **LIVE VERIFICATION**, not previously proven production behavior.

## Controlled first broadcast — proposed only

Prerequisites: all BLOCKERs resolved; explicit separate approval for the actual registration transition and live test; backup/recovery owner available; actual URLs, deployed revisions, queues, administrator authorization and institution UUID confirmed. The transition has real registration effects, so obtain the university administrator's operational approval and establish the original state and an approved post-test plan. Do not close registration merely to manufacture a test; if it is already open, an open request is a no-op and cannot generate the desired event. Stop and arrange a separately approved scenario.

1. Review pending events and delivery terminal reasons without changing them. Confirm no historical events will be unexpectedly sent, assess stale aggregate versions, and confirm no unsupported row can block supported events. Preserve evidence without exposing student data or secrets.
2. Sign in two authorized students in separate browser sessions and confirm their trusted mappings belong to the configured institution. Where authorized, have a separate-institution negative-control account. Open the notification views; verify API Auth, CORS and stream/poll status.
3. With registration confirmed closed and explicit transition approval, an administrator authenticated through the existing Fake University Auth path calls `POST /v1/admin/registration/open` on the persistent university backend with its bearer token and a fresh, unique `Idempotency-Key`. Optional `start`/`end` must be agreed by the administrator. Protect tokens from shell history and logs. No registration-open admin UI was found; the existing authenticated API is the documented route. Do not use the Vercel synthetic API as a substitute.
4. Correlate the returned event ID and key with exactly one persisted `registration.opened` event, a successful delivery attempt, and one receiver inbox/notification row for the configured university. Check both student bells and the negative-control account, without revealing private data. Refresh both pages to verify persistence.
5. With separate approval and an explicitly reviewed safe replay mechanism, resend the exact signed event or retry the exact original open request/key; verify no extra notification and no side effects. The ordinary admin retry proves command idempotency but does not by itself prove duplicate HTTP webhook handling. Never generate a new key for a retry. Do not reuse a historically no-op key as a new open command; pre-ledger no-ops have no durable record. Any requeue/replay of terminal events needs its own reviewed procedure.
6. Record counts, event IDs, statuses, timing, stream/poll behavior and release revision without secrets. If the delivery fails, stop and investigate; do not repeatedly toggle registration.

## Gates and proposed sequence

**BLOCKER** — production values and actual backend routing unverified; HMAC-to-university binding and privileged users unverified; neither production migration ledger nor schema compatibility checked; release files uncommitted and temporary files accidentally stageable; independent free-elective migration ownership unresolved; backup, rollout, quiescence and recovery approvals absent; queued events and version history unreviewed; actual persistent sender restart behavior untested; full application release gates and historical baseline failures not newly assessed.

**LIVE VERIFICATION** — hosted proxy/SSE behavior, real browser and polling fallback, real sender-to-receiver connectivity, live two-university negative control, explicit duplicate replay, and approved registration transition. These follow only after blockers are resolved and the owner authorizes them.

After separate human approvals: (1) verify current remote heads and explicitly select/review intended files while excluding temporary directories and unrelated work; stage only those files, review staged diffs and secret-scan; (2) separately approve and create commits, then separately approve pushing them; (3) have operators inspect production migration ledgers, approve backup and recovery, quiesce all old notification readers/ingress and sender workers, and apply only reviewed pending migrations in dependency order; (4) deploy scoped Morshidi receiver and compatible persistent university sender, verify revisions/configuration and resume traffic under a controlled plan; (5) perform nonmutating health and access checks; (6) obtain explicit approval and run the first broadcast procedure. This audit executes none of those release actions.
